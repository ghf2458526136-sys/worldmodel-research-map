# 2026 世界模型论文：引用速率与「被继承」之外的影响力指标

讨论稿 · 2026-10-21 · 基于 research-map.yaml（124 节点 / 8 泳道）与 citations.json 实测

---

## 0. 结论先行

引用速率测的是**外部注意**，「图谱内被继承次数」测的是**内部谱系**。这两者之间空着两块：论文的机制有没有被后来的工作**吸收成默认做法**（概念扩散），以及有没有人**真的把代码跑起来**（工程采纳）。

但在这份语料上，我不建议把它们压成一个「影响力总分」。原因是三个统计事实（见 §1）：79% 的论文是 2026 年的、24% 是本月上传的、90.8% 的论文引用为 0。任何单一标量都会把最新那批直接判死，而它们恰恰是图谱存在的理由。

建议的做法是**三个互不换算的分维度**（学术注意 / 谱系繁衍 / 工程采纳）＋ 一条**按论文类型切换口径**的规则（§7）。总分只在内部筛候选时用，不上页面。

## 1. 语料实况：先看哪些指标根本不可用

2026-10-21 快照实测：

| 事实 | 数字 | 对指标的约束 |
|---|---|---|
| 节点 / 泳道 | 124 / 8 | 样本量小，任何比例型指标的分母都很薄 |
| 2026 年论文 | 98 篇（79.0%） | 主流计量指标的时间窗还没打开 |
| 2026-10 论文 | 30 篇（24.2%，月龄 <1） | 累积量与「÷月龄」在这批上必然失真 |
| 2026 年有引用的论文 | 3 篇 | 2026 子集内引用几乎无区分度 |
| 有 arXiv 号 | 112 篇（90.3%） | 学术侧 API 匹配可行；12 篇只能人工 |
| 有引用字段 / 其中为 0 | 109 / 99（90.8%） | 零膨胀：均值 0.9，中位数 0，最大 47 |
| 非零引用分布 | CausVid 47（2024-12）、Self-Forcing 42（2025-06）、WorldScore 17（2025-04）、FramePack 7、SPMem 6，其余 ≤2 | 真正有信号的只有 4-5 篇 |
| 有 parent 的节点 | 19 篇（边密度 15.3%） | betweenness、传递闭包这类结构指标目前是噪声 |
| 有 GitHub 链接 | 28 篇（22.6%） | 工程类指标覆盖率不足 1/4 |
| 日期精度 | 22 篇到日 / 39 篇标 month / 62 篇未标 precision | 月龄有 ±半月不确定度 |

三个后果，直接决定指标设计：

1. **零膨胀 + 右删失**。2026-10 的 30 篇在快照时点**不可能**被引用或被继承，这不是「影响力低」，是「还没暴露」。指标必须能输出 `N/A（月龄 0.7）`，而不是 0。当前实现把缺失和零混在一起，是最大的口径错误。
2. **覆盖率分层**。引用 87.9%（109/124）、arXiv 90.3%（112/124）、GitHub 22.6%（28/124）、HF 更低。「缺失」在不同论文上含义完全不同（闭源产品论文天生没有仓库），所以**覆盖率 <50% 的指标不能当排序键**，只能当卡片补充字段。
3. **边太稀**。19 条边下，中心性指标全部不稳定；要么先补边到 ≥60 条，要么改用「跨泳道边数」这种粗粒度计数。

另外，「引用速率 = 引用数 ÷ 发表月数」这个式子本身有两个可修的问题：

- **分母不确定度**：62 篇只有月粒度，对月龄 1-2 月的论文，速率相对误差 17-33%。
- **除法的病态**：1 引用 ÷ 1 月 = 12 次/年，噪声放大 12 倍；0 引用 ÷ 12 月 = 0，与「没人理」不可区分。
- 建议改成**同月龄、同泳道内的分位（rank）**，或做贝叶斯平滑：`rate = (c + α·π_lane) / (months + α)`，α≈3，π_lane 为该泳道引用率的先验中位数。分位不假设线性，也不怕零膨胀。

## 2. 评级口径

**可算性**

| 级 | 含义 | 工作量 |
|---|---|---|
| A | 现有 YAML 一次遍历即可，0 外部请求 | 分钟级 |
| B | 需一次性抓取脚本 + 标题/arXiv 匹配，有公开 API | 1-3 小时，可缓存 |
| C | 需多源拼接或人工抽验，precision 不可保证 | 半天以上，需人 |
| D | 无公开数据源，只能人工判断 | 不建议进流程 |

**风险**（指「这个数会骗人」的程度，而非实现难度）

| 级 | 含义 | 允许的用法 |
|---|---|---|
| 低 | 口径稳定、偏差可解释、样本内可比 | 可进排序、可展示 |
| 中 | 有系统性偏差（年龄、平台、类型），方向可信、量级不可信 | 只做提示/徽章，不进总分 |
| 高 | 覆盖率 <30% 或定义主观、易被操纵 | 仅作定性证据，写进报告正文 |

## 3. 视角一：学术计量 —— 学界有没有认真对待它

| # | 指标 | 定义 / 公式 | 数据源 | 可算性 | 风险 | 主要失效模式 |
|---|---|---|---|---|---|---|
| A1 | 影响力引用数 | S2 `influentialCitationCount`，只算「实质性引用」 | Semantic Scholar Graph API | B | 中 | 2026 预印本收录滞后；短窗内恒 0 |
| A2 | 引用意图加权 | methodology/intent 引用占比 = 方法类引用 / 总引用 | S2 `/citations?fields=intents,contexts` | C | 高 | 分类噪声大；n<5 时比例不稳 |
| A3 | 引用来源多样性 | 引用方 venue / 机构 / 国家的熵（或 1−Gini） | OpenAlex `filter=cites:W…` | B | 中 | 小 n 下熵极敏感；自引族会虚高 |
| A4 | 净他引率 | 扣除同作者、同机构、同族续作后的引用数 / 总引用 | OpenAlex authorships + institutions | B | 中 | 作者消歧错、机构挂错；需人工抽验 |
| A5 | 综述收录 | 是否进入后续世界模型综述的 related work | 人工 + 语料内「评测基准」节点近似 | D→C | 高 | 时滞 12-18 月，对 2026 论文几乎全 0 |

**视角内取舍**：A1 和 A4 值得做，且应该一起做——单独看总引用，Self-Forcing（42）和 CausVid（47）的差距没意义，但扣掉同族续作后，Self-Forcing 的外部采纳其实更广，这才是「影响力」而不是「一个团队自己引用自己」。A3 的正确用法不是算熵，而是画一张「引用方都来自哪几个组」的小名单：124 篇的规模下，名单比数字更有信息量。A2、A5 建议放弃自动化，只在正文里对 2-3 篇做定性证据（「WorldScore 被 X、Y、Z 当作评测协议」比任何分数都硬）。

**一个必须接受的现实**：对 2026 年这批论文，学术计量在未来 6 个月内基本不产出信号。如果页面上把引用速率做成主视觉，等于让 90% 的卡片显示 0，读者会得出「这个领域没什么影响力」的错误结论——这是当前实现最大的叙事风险。

## 4. 视角二：谱系繁衍 —— 它在这个领域里长出了什么

「被继承次数」只数了直接子节点，剩下四种信息都没被用：

| # | 指标 | 定义 / 公式 | 数据源 | 可算性 | 风险 | 主要失效模式 |
|---|---|---|---|---|---|---|
| B1 | 后代总数（传递） | 子图内可达节点数（含间接后代） | YAML parent 边 + 闭包 | A | 中 | 19 条边下不稳定；深度 2 层就断 |
| B2 | 跨泳道扩散广度 | 后代覆盖的不同 lane 数 / 8 | 同上 + lane 字段 | A | 中 | lane 是人工分类，边界主观 |
| B3 | 被继承时延 | 首次被继承的月数；**必须带右删失标记** | 节点 date 差 | A | 低 | 仅对 ≥3 月龄论文有意义 |
| B4 | 净继承 | 扣除同团队/同族续作后的外部继承数 | parent 边 + 人工 20-30 条判定 | B | 中 | 团队归属需作者消歧 |
| B5 | 桥接度 | 连接不同 lane 的最短路径经过次数 | 需 ≥60 条边 | C | 高 | 当前边密度下纯噪声 |
| B6 | 术语/机制扩散 | 该节点方法名或 coined term 在**更晚论文摘要**中的出现率 | arXiv API（112 篇摘要）+ 正则 | B | 中 | 术语泛化、同名误检；缩写要白名单 |

**展开 B2 和 B6，这两个是被低估的。**

B2 回答的是「这个想法有没有跨出自己那条线」。位置时间寻址里的一篇 sink 类工作，如果只被同分支继承，那它是**分支内的迭代**；如果被几何位姿寻址的论文也拿去用，那它是**领域级贡献**。8 条泳道给出 0-8 的天然刻度，比「被继承 2 次」可解释得多。实现只需在现有 parent 边上多带一个 lane 字段做 groupby，成本几乎为零。

B6 是唯一一个能绕开引用时滞的概念性指标。做法：取每篇论文标题里的方法名（Self-Forcing、CausVid、FramePack…），在**发表日期更晚**的语料论文摘要里做大小写不敏感匹配，命中率 = 扩散度。它测的是「术语有没有被吸收」，通常比引用早 3-6 个月出现。风险是缩写误检（`MIND`、`MOC` 这种词必须走词边界 + 白名单），所以只对 20-30 个独特方法名跑，别全量。

**B4 值得人工做一次**：19 条边全部人工复核也就半小时，但能把「同族续作」和「外部继承」分开。这一步不做，图谱的谱系叙事会被「一个实验室自己发了一串」污染，而这在 2026 年的世界模型里非常常见（CausVid → Self-Forcing 就是同族链）。

## 5. 视角三：工程与生态 —— 有没有人真的跑它

| # | 指标 | 定义 / 公式 | 数据源 | 可算性 | 风险 | 主要失效模式 |
|---|---|---|---|---|---|---|
| C1 | 星标增速 | stars / 月（不是绝对 stars） | GitHub API（未认证 60 req/h） | B | 中 | 覆盖 28/124=22.6%；刷星；老仓库积累优势 |
| C2 | 代码活跃度 | 近 90 天 commit 数、open issue、fork 存活率 | GitHub API | B | 中 | fork 僵尸多；issue 数受模板影响 |
| C3 | 权重/数据下载 | HF `downloads` / `likes`（模型与数据集） | HF API `api/models?search=` | B | 中 | 覆盖 ~15%；下载含 CI 爬虫；likes 易刷 |
| C4 | 榜单留痕 | 是否出现在官方/社区 leaderboard 的评测名单 | 基准仓库 README / 榜单页 | C | 中 | 只有进 benchmark 的方法有；需爬 HTML |
| C5 | 复现/衍生仓库数 | GitHub 搜索方法名，去重后计数 | GitHub search API | C | 高 | 命名变体漏检、同名误检；precision 需抽验 |
| C6 | 产业提及 | 技术报告/公司 blog/产品页出现 | 无 API | D | 高 | 公关偏差，不可复现 |

**视角内取舍**：C1 必须用**增速**而不是绝对数——2024-12 的 CausVid 和一个 2026-09 的仓库比总 stars 毫无意义，这跟引用速率是同一个病。C4 是这个视角里最被低估的：我们语料里有 18 篇「评测基准」，它们的「影响力」本来就不体现为被继承，而体现为**被谁的榜单收进去评测**。WorldScore / WorldModelBench 的仓库里就列着被评模型清单，那是可以直接抓的结构化数据，而且比 stars 干净得多。

C5 我标了高风险但值得做一次：目的不是得到精确计数，而是拿到一份「谁复现了谁」的候选名单，人工看 20 条就知道漏检率。如果漏检 >40%，这个指标就该砍掉，而不是硬修。

C3 的现实是覆盖率太低（开源放权重的才 ~15%），只适合当个别卡片上的「有官方权重」标签，不适合做维度分。

## 6. 三个视角的冲突，以及怎么裁决

**冲突一：学术视角说「等引用」，谱系视角说「引用现在没用」。**
两者都对，但适用范围不同。判断依据是月龄：≥12 月的论文（本语料约 20 篇）用引用计量；<6 月的（本语料 77 篇）只能用谱系和工程信号。所以正确的产品形态不是「一个指标」，而是**按月龄切换主指标**，并在卡片上标出当前用的是哪把尺。这比任何复合公式都诚实。

**冲突二：谱系指标有确认偏差。**
边是我们自己标的，我们读过、觉得重要才连上，于是「被继承多」部分反映了我们的阅读顺序。缓解办法：把**边密度**（当前 15.3%）作为置信度一起展示；边密度低于某个阈值时，谱系指标的措辞从「影响力」降级为「本图谱内的位置」。这是措辞问题，不是算法问题，但决定了读者会不会被误导。

**冲突三：工程信号对最新论文是先行指标，但也是噪声源。**
2026 年这批论文里，stars 通常在引用出现前 6-12 个月就有动静，所以它对「现在该关注谁」有预测价值；但 star 数受发布时机、Hacker News 曝光、作者推特影响极大，跨论文不可比。裁决：工程信号只做**同一泳道内**的相对比较，不跨泳道。

**三方一致才是强信号。** 三个视角都高的（Self-Forcing：42 引用 + 高净他引 + 被多篇 2026 论文继承 + 有社区复现）可以放心标「高热」；只有单维度高的必须给类型解释：WorldScore 是基准论文（17 引用 + ICCV），它的影响力形式是「被当评测协议用」，用「被继承」去衡量它本身就是错的。

## 7. 按论文类型分口径（最容易踩的坑）

124 篇里论文类型并不单一，用一把尺量全部会系统性冤枉某一类：

| 类型 | 数量 | 主指标 | 不该用的指标 |
|---|---|---|---|
| 方法/框架 | ~70 | 净继承 + 跨泳道扩散 + 引用速率分位 | 榜单留痕 |
| 评测基准 | 18 | 被榜单/对比表采纳（C4）+ 引用 | 被继承（基准很少被继承） |
| 训练技巧/蒸馏 | 14 | 净继承 + 术语扩散（B6） | stars（多数不发代码） |
| 闭源产品/框架层 | 15 | 产业提及（C6，定性）+ 被讨论度 | GitHub/HF 任何指标 |
| 综述/位置论文 | 少量 | 综述收录（A5） | 全部量化指标 |

这张表的价值在于：它解释了为什么「同一张图谱里 WorldScore 看起来很弱」——不是它弱，是我们的尺不对。

## 8. 落地建议

**P0（今天就能上，纯图谱，0 外部请求）**
1. 引用速率改成**同月龄同泳道分位**，并把月龄 <3 的输出为 `N/A`。
2. 被继承拆成「直接 / 传递 / 跨泳道」三个数（B1、B2）。
3. 被继承时延带右删失标记（B3）。
4. 卡片上显示边密度，作为谱系指标的可信度注脚。

**P1（一次性脚本，需 API key）**
5. S2 `influentialCitationCount` + 净他引率（A1、A4）——先只对 10 篇非零论文做，成本可控。
6. 术语扩散（B6）：112 篇 arXiv 摘要 + 20-30 个方法名。
7. stars 增速（C1）：28 个仓库，一次扫描缓存成 JSON，别放进每次 build。

**P2（只进报告/评审，不进页面）**
8. 引用意图（A2）、复现仓库数（C5）、榜单留痕（C4）、产业提及（C6）。

**如果一定要一个内部排序分（不上页面）**

```
score = 0.40·z(log1p(净继承)) + 0.25·z(log1p(跨泳道继承数))
      + 0.20·z(引用速率分位)  + 0.15·z(工程采纳分, 缺失取泳道中位数)
```

三条禁用规则：
- 缺失值不许当 0（闭源论文的 stars 缺失 ≠ 没人用）。
- 月龄 <3 的论文不参与排序，只打「新」标。
- 这个分只在同泳道内比较，跨泳道无意义（基准论文和方法论文的量纲不同）。

**回测方案（决定哪个指标值得留）**：用 2023-2025 年那 26 篇（月龄 ≥10）的论文，算各指标与「12 个月后引用」的 Spearman 相关。现在有信号的只有 4-5 篇，样本很小，但至少能验证「跨泳道扩散」是否真的比「直接继承」更预测后续引用。没有回测就上复合分，等于相信自己的直觉。

## 9. 反模式清单

| 别做 | 原因 |
|---|---|
| h-index / i10 | 90.8% 的论文引用为 0，这两个指标全为 0 |
| 期刊影响因子 | venue 字段覆盖极少，且世界模型主流是 arXiv 预印本 |

| 跨月龄直接比引用 | 2026-10 的 30 篇会被系统性判死 |
| 把同族续作算作继承 | CausVid → Self-Forcing 这类链会虚高整条家族 |

## 10. 待核实项与运维风险（今天实测踩到的）

- **OpenAlex 免费额度按 IP 共享**，今天直接打爆：`Insufficient budget … $0 remaining, resets at midnight UTC`。引用类指标必须申请免费 key（`POST https://api.openalex.org/api-keys`），否则任何「每天刷新」的设计都会随机失败。
- **Semantic Scholar 无 key 直接 429**（`Too Many Requests`），`influentialCitationCount` 需要 key，限制约 1 req/s。
- **GitHub 未认证 60 req/h**（已确认 `rate_limit` 返回 60），且 `graphql` 未认证为 0。28 个仓库一次扫描够，但不能进 CI。
- **OpenAlex 的 arXiv 预印本记录 referenced_works 常为空**（实测 StreamingLLM `arXiv:2309.17453` 的 `referenced_works_count=0`）→ 不要指望从 OpenAlex 建语料内引用边，只能走被引方向 `filter=cites:W…`。
- **Papers with Code 已于 2025 年下线**（待最终核实），「榜单留痕」信号要改从基准仓库 README / HF leaderboards 取。
